## 0. 需求理解

### 0.1 能力分解

| 编号 | 能力 | 说明 |
|---|---|---|
| P0 | 起终点采集 | 经纬度手工输入 + 地图点击选点，交互对齐灾害模块的"灾害位置"输入 |
| P1 | 起终点吸附 | 自由坐标 → 最近路网节点，返回吸附偏差 |
| P2 | 最短路径求解 | 基于 `road_node` / `road_edge` 有向图，求节点序列 → 边序列 |
| P3 | 结果可视化与清单 | 地图绘制路线；提取途经桥梁/隧道并沿用现有 `judge()` 出判定 |
| P4 | 保通路径规划 | 人工指定某桥/隧禁行 → 其绑定边不可通行 → 重解绕行路径 |

### 0.2 本期明确的边界（不做）

- 不做地址解析 / POI 搜索（路网无地址库，文本输入一律按经纬度或地图点选）；
- 不做到边投影吸附（P0 只吸到最近节点，见 §5-A3）；
- 不实现 `preference` 三档权重（`DISTANCE` / `TIME` / `SAFETY`），本期统一按里程，见 §3；
- 不做 K 条备选路线、不做异步任务、不引外部引擎；
- 不改动灾害、韧性、首页模块。

### 0.3 功能载体

重车通行评估面板。左侧第一块 `tech-panel` 改为"路径规划"面板（原"重车任务配置"下移），面板内包含：起点/终点经纬度输入、两个"地图选点"按钮、吸附结果回显、执行按钮。地图中央区域绘制路线；右侧"沿线桥隧判定"列表复用，增加"禁行/恢复"操作作为 P4 入口。

## 2. 规模与单次耗时评估

### 2.1 规模基线

| 项 | 数量 |
|---|---|
| 节点 | 8,488 |
| 边（有向记录） | 11,742 |
| 建图后弧数（双向边补反向） | 12,832 |
| 总里程 | 24,891 km（平均边长 2.12 km） |
| 几何顶点（按 OSM 60–120 m 点距估算） | 20 万 ~ 40 万 |
| 桥隧 / 绑定关系 | 11 / 21 |

### 2.2 一次性建图（懒加载，仅首次）

| 步骤 | 估算 |
|---|---|
| MySQL 拉 11,742 行（含 WKT 约 5–8 MB） | 300–800 ms |
| WKT `LINESTRING` 解析（20–40 万顶点） | 30–80 ms |
| 邻接表 + 边属性装配 | 10–20 ms |
| **合计** | **约 0.5–1.5 s** |

内存占用：节点 0.4 MB + 弧 0.9 MB + 几何 3.2–6.4 MB ≈ **5–8 MB**。可常驻。

### 2.3 单次规划（图已就绪）

| 步骤 | 估算 |
|---|---|
| 起终点吸附（8,488 节点线性 haversine） | 0.3–0.8 ms |
| Dijkstra（12,832 弧，二叉堆） | 2–5 ms |
| 若同时求备选（第二次 Dijkstra） | +2–5 ms |
| 沿线桥隧反查 + `judge()` | < 0.1 ms |
| 几何拼接（50–200 边 × 20–40 点 = 1k–8k 点） | 1–3 ms |
| JSON 序列化 + 传输（20–180 KB） | 5–20 ms |
| 落库（`analysis_task` + `analysis_result`） | 5–15 ms |
| **合计（服务端）** | **约 15–50 ms** |

### 2.4 结论

- 11,742 条边对内存图算法**完全不构成压力**，单次规划毫秒级，无需预计算、缓存、异步或外部引擎；
- **真正的瓶颈是返回几何的体积**（1k–8k 个坐标点的 JSON），不是算法本身。若后续出现卡顿，优先压缩点位（6 位小数 / 去重复端点 / 5 m 容差 Douglas-Peucker 简化可减 40–60%），而不是换算法；
- 保通路径重算是"再跑一次 Dijkstra"，边际成本≈0，适合做成即时交互。
- 估算需在阶段 1 用实测校准：建图与求解耗时写入服务端日志（`graphBuildMs` / `solveMs`），并回填到本文档。

## 3. 算法选型

### 3.1 候选对比

| 算法 | 适用前提 | 复杂度 | 本项目判断 |
|---|---|---|---|
| BFS | 无权图 | O(V+E) | 只能比跳数，无法比里程 → 弃 |
| **Dijkstra（二叉堆）** | 非负权 | O(E log V) | **首选**。8.5k 节点/12.8k 弧约 10⁵ 量级堆操作，代码约 60 行，结果确定可复现 |
| A*（启发式 = 球面距离 ÷ 最大设计速度） | 同上 | 扩展量降至 1/3–1/10 | 二期优化。加惩罚权重后启发式须仍"可采纳"，易写错，本期不做 |
| 双向 Dijkstra | 同上 | ≈ 2× | 二期 |
| Bellman-Ford / SPFA | 允许负权 | O(VE) | 无负权 → 弃 |
| Floyd-Warshall | 全源最短路 | O(V³) ≈ 6×10¹¹ | 完全不可行 → 弃 |
| Yen K-最短路 | K 条互异路径 | K × Dijkstra | 二期；初期以"惩罚重跑"替代（§3.3） |
| CH / ALT / Hub Labeling | 全国级路网 | 预处理重、实现复杂 | 过度设计 → 弃 |
| OSRM / GraphHopper / pgRouting | 外部引擎 | — | 引入部署与运维成本，1.2 万边不值 → 弃 |

### 3.2 选择

**Dijkstra + 二叉堆（`java.util.PriorityQueue`）**，边权 = `length_m`。

理由：目标"简单快速跑通"，Dijkstra 无启发式正确性风险、无参数、可解释（答辩时能一句话说清），性能已远超需求（5 ms 级）。A* 是纯优化项，留到有实测瓶颈时再加，且届时只需换比较函数，接口不变。

### 3.3 保通路径的算法处理

**不引入新算法**：同一个 Dijkstra，增加"边禁用集合"参数，被禁用边（含其反向弧）权重置 `Double.POSITIVE_INFINITY` 或直接跳过出边。

```
solve(origin, destination, Set<Long> disabledEdgeIds) → Path
```

这一签名同时覆盖三种需求：
1. P4 人工禁行 → 传 `closedEdgeIds`；
2. 未来韧性模块"受损路网重算" → 传损伤边集合 + 通行能力系数；
3. 未来 `avoidBlocked` 生效 → 传判定为 BLOCKED 的边集合。

**架构要求**：图对象不可变，禁用集合作为**查询参数**传入，绝不修改图本体。否则并发请求互相污染，且韧性阶段必须重写。

### 3.4 备选路线（二期，但接口预留）

对推荐路径的每条边权重乘惩罚系数 `1.6` 后再跑一次 Dijkstra。简单、可解释、必然产出不同路径。不用 Yen。

## 4. 技术方案

### 4.1 分层

```
HeavyController#evaluate            ← 只做入参/出参（几乎不动）
  └─ HeavyService#evaluate          ← 编排：规划 → 沿线判定 → 落库
       ├─ RoadGraphService          ← 新增：内存有向图（不可变快照 + overrides 查询）
       │    ├─ build()              懒加载，synchronized 双检，记录 buildTime/耗时
       │    ├─ snap(lon,lat)        最近节点 + 偏差米数
       │    └─ graph()              返回只读快照
       ├─ PathFinder                ← 新增：Dijkstra，接受 disabledEdges
       └─ FacilityRuleService       ← 新增：由 HeavyService#judge 抽出，规则零改动
```

- 全部为普通 Spring `@Service`，无新依赖（`pom.xml` 现只有 web / jdbc / mysql；`LINESTRING` 自写解析，约 30 行，不引 JTS）；
- 控制器不加新端点，`POST /api/heavy/evaluate` 增量扩展，避免前端两套调用。

### 4.2 图数据结构

```
nodes: long[] id  / double[] lon, lat  / int[] componentId
adjHead: int[]  (CSR 或 List<int> 起止)
arcs: from, to, edgeId, weightLengthM, geometryIndex
edgeGeom: double[][] {lon,lat,...}     // 按 edgeId 索引，供拼接
edgeAsset: Map<Long, Long>             // edgeId → assetId（21 条）
```

节点重编号为 `0..N-1` 的连续索引（`HashMap<Long,Integer>` 一次性映射），Dijkstra 用 `double[] dist` + `int[] prev` 数组，避免对象分配。

### 4.3 拓扑规则

- `one_way = true` → 只建 `from → to` 一条弧；
- `one_way = false` → 建 `from → to` 与 `to → from` 两条弧，**反向弧的几何必须反转坐标序列**；
- 建图时计算弱连通分量标签，OD 不同分量时直接返回不可达，不进入搜索。

### 4.4 吸附规则（P1）

最近节点按 haversine 距离取最小，返回 `snapDistanceM`。边界情况：

| 情况 | 处理 |
|---|---|
| 吸附偏差 > 2,000 m | 仍返回路径，但在结果中标注"起点距路网较远（X km），接入段未纳入计算" |
| 起终点吸附到同一节点 | `distanceKm = 0`，返回提示而非空路径 |
| 坐标不在重庆范围（约 105.2–110.2E / 28.1–32.2N） | 400 错误，明确提示，不落到"不连通" |

### 4.5 接口契约

**请求**（在现有字段上增量；`origin/destination` 两个旧字符串字段废弃，但后端容忍缺失）

```json
{
  "taskName": "重车通行评估任务",
  "grossWeightTon": 100, "vehicleLengthM": 18, "vehicleWidthM": 3.2,
  "vehicleHeightM": 4.5, "axleCount": 6, "plannedSpeedKmh": 30,
  "originLongitude": 106.5518, "originLatitude": 29.5634,
  "destinationLongitude": 106.6055, "destinationLatitude": 29.5901,
  "avoidBlocked": true, "allowConditional": true, "preference": "SAFETY",
  "vehicleProfileId": 1,
  "closedAssetIds": []
}
```

**响应**（保留全部旧字段，`recommendedDistance` / `alternativeDistance` 改为由真实路径回填，前端旧代码不炸）

```json

  "id": 123, "taskCode": "HEAVY-000123", "taskName": "...", "status": "SUCCESS",
  "rows": [ { "assetId": 7, "status": "CONDITIONAL", "reason": "...", "action": "...",

    { "key": "recommended", "label": "安全推荐路径",
      "distanceKm": 38.4, "durationMin": 46,
```

`points` 坐标顺序统一 **[lat, lng]**（与 Leaflet 一致）；DB 中 `geom` 为经度在前，转换只在图服务一处完成。

### 4.6 前端交互

1. **左侧第一面板「路径规划」**
   - 起点：经度 / 纬度 两个数字输入框 + 「地图选点」按钮；
   - 终点：同上；
   - 吸附回显：执行后显示 "起点吸附：XX 高速，偏差 320 m"；
   - 「⇅ 起终点互换」保留。
2. **点选模式**：`pickMode` 由单值改为 `'' | 'origin' | 'destination'`，`TransportMap` 复用 `is-picking` 光标；地图面板顶部复用 `map-pick-banner` 显示"在地图上点击选取起点"并提供取消。
   - 需扩展 `TransportMap`：新增起点/终点两个标记 prop（现有只支持 `epicenter` 一种点）。
3. **画线**：`mapRef.drawRoutes([{ points, style }])`。推荐线 `#45e4ff` weight 5（沿用现有常量）；保通绕行线 `#ff6b35` weight 5（橙色在语义表里已是"受灾害/中断影响"，正好与"因禁行绕行"契合）；备选线 `#a187ff` 虚线（二期）。
4. **右侧「沿线桥隧判定」**：每项增加「设为禁行 / 恢复通行」操作，触发 P4 重算，并显示里程增量。
5. **路线卡片**：`durationMin` 改读后端字段（现有代码用 `distance / plannedSpeed` 估算，会与真实路径不一致）。

## 5. 潜在问题与应对

### A. 数据与拓扑（风险最高，且代码无法解决）

| 编号 | 问题 | 影响 | 应对 |
|---|---|---|---|
| A1 | **连通分量数量未知**。OSM 高速/干线裁剪网可能碎成多块 | 跨块 OD 直接无解，演示时可能第一次点击就失败 | 阶段 0 实测；结果决定是否需要在 UI 上限制可选区域 |
| A2 | **正反向可达性不对称**。`one_way=true` 10,652 条 + 匝道方向 | "A→B 有路、B→A 无路"，而前端有互换按钮 | 阶段 0 统计强连通性；不可达时明确提示"该方向无可通行路径" |
| A3 | **节点吸附偏差达公里级**（平均边长 2.12 km） | 路线起点不在用户点的位置，看起来"绕远" | 本期接受，返回 `snapDistanceM` 并明确提示；二期考虑边投影切分 |
| A4 | **几何方向一致性未验证**。`geom` 首点是否等于 `from_node` 未测 | 反向通行拼接会画出折返线，视觉错误但难排查 | 阶段 0 用 SQL 校验首末点与节点距离 |
| A5 | **匝道未渲染**。`/api/map/roads` 过滤 `REGEXP '(^|;)(motorway|trunk)($|;)'`，5,736 条 `*_link` 不在底图上 | 路径有一半悬在没有底图的空中 | 本期：路线线本身带几何，能画出来，但需在图例说明"路径含匝道"；二期放开底图过滤或单独图层 |
| A6 | **桥隧绑定稀疏**：21 条关系覆盖 11,742 边 | 沿线清单大概率为 0–2 条，甚至空 | 接受；UI 空态文案写"本路径未途经已建库桥隧"，不要写"无风险" |

### B. 业务语义

| 编号 | 问题 | 应对 |
|---|---|---|
| B1 | **`rows` 语义冲突**：现为全量 11 座，改沿线后若路径无桥隧则 `rows` 为空，现有 `pending == rows.size()` 会误判 `PENDING_DATA` | **[待定]** 两个方案见 §7-D1 |
| B2 | **禁行粒度**：一座设施平均绑定 1.9 条边（21/11） | 禁行 = 禁用该 `assetId` 名下**全部**边 |
| B3 | **禁行后无解**（如跨江桥是唯一通道） | 返回 `reachable:false` + `unreachableReason`，前端红字提示；不得 500 |
| B4 | **禁行与规则叠加**：人为禁行的设施仍应出现在 `rows` 中 | 状态置 `BLOCKED`，`reason = "人工指定禁行"`，`source = "MANUAL"`；`judge()` 结果被覆盖 |
| B5 | **保通缺少对照**，使用者看不出代价 | 返回 `distanceDeltaKm` / `durationDeltaMin`，卡片显示"绕行 +6.2 km / +8 min" |
| B6 | `avoidBlocked` / `allowConditional` 现为"仅影响结论文字"，不参与选路 | 本期明确：**它们开始影响选路**（BLOCKED 边剪枝）。这是行为变更，需在 UI 文案说明 |

### C. 前端与交互

| 编号 | 问题 | 应对 |
|---|---|---|
| C1 | `pickMode` 单值无法区分起终点 | 扩为 `'origin' \| 'destination'` |
| C2 | 起终点只有经纬度，卡片标题可读性差 | 用吸附节点所在 `road_name` + `road_ref` 生成标签 |
| C3 | 经纬度输入顺序易混、超范围无提示 | 输入框标注 E/N 与合法范围，提交前校验 |
| C4 | 时间估算口径不一致 | 统一读 `durationMin` |
| C5 | 新增第三种线色缺图例 | 图层弹层补充图例项 |

### D. 工程

| 编号 | 问题 | 应对 |
|---|---|---|
| D1 | `judge()` 是 `HeavyService` 的 `private static`，路径服务无法复用 | 抽 `FacilityRuleService`，规则体不改一字，`HeavyService` 委托调用 |
| D2 | 建图并发重复触发 | `synchronized` 双检 + `volatile` 快照引用 |
| D3 | 路网数据更新后内存图过期 | 提供 `POST /api/admin/road-graph/rebuild`（管理端），并在响应里回传 `builtAt` 供排查 |
| D4 | `routes.points` 写入 `analysis_result` 使单任务 JSON 增至数十 KB | 坐标 6 位小数；必要时提取"逐边几何"而非整条折线 |
| D5 | 历史任务回放无 `routes` 字段 | 前端一律 `result.routes?.[0]?.distanceKm ?? result.recommendedDistance` 容错 |

## 6. 分阶段落地

| 阶段 | 内容 | 产出 | 验证 |
|---|---|---|---|
| **0** | 数据体检（只读，不改代码） | 连通分量数、正反向可达性、几何方向一致性、吸附样例、桥隧绑定分布 | 一份结论表，回填本文档 §5-A |

## 8. 阶段 0 数据体检脚本（待执行）

均为只读查询，建议导入 `database/validation/` 作为长期校验项。

```sql
-- 1) 几何方向一致性：geom 首点应等于 from_node，末点应等于 to_node（容差 20 m）
SELECT COUNT(*) AS bad_from
FROM road_edge e JOIN road_node n ON n.id = e.from_node_id
WHERE ST_Distance_Sphere(ST_StartPoint(e.geom), n.geom) > 20;

SELECT COUNT(*) AS bad_to
FROM road_edge e JOIN road_node n ON n.id = e.to_node_id
WHERE ST_Distance_Sphere(ST_EndPoint(e.geom), n.geom) > 20;

-- 2) 桥隧绑定边的空间分布（判断沿线清单能否非空）
SELECT a.asset_name, a.asset_type, e.id, e.road_name, e.road_ref, e.length_m, e.one_way
FROM asset_road_relation r
JOIN transport_asset a ON a.id = r.asset_id
JOIN road_edge e ON e.id = r.road_edge_id
ORDER BY a.asset_type, a.asset_name;

-- 3) 给定坐标的最近节点与偏差（以解放碑 106.5518,29.5634 为例）
SELECT id, ST_Distance_Sphere(geom, ST_SRID(POINT(106.5518, 29.5634), 4326)) AS d_m
FROM road_node ORDER BY d_m LIMIT 5;
```

连通分量、正反向可达性、单/双向比例这三项 SQL 表达不了，做法是导出 `id, from_node_id, to_node_id, one_way` 四列（11,742 行）到 CSV，用 Python 并查集 + Tarjan 计算，秒级完成，不写库。
