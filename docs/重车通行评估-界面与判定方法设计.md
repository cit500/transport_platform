| 事实 | 对本设计的影响 |

## 1. 调研一：界面重设计

### 1.1 四条用户流程

**流程 A · 规划**（已实现）：起终点（输入/选点/互换）→ 最短路径 → 沿线桥隧清单。

**流程 B · 全线评估**（新增）：选车辆方案 → 「执行通行评估」→ 对沿线每处桥隧跑五维规则链 → 清单条目与地图标记从"待核查"变为四色 → 底部出现"评估结论"。

**流程 C · 保通路径规划**（新增）：出现 BLOCKED（或用户手动禁行任意沿线设施）→ 保通面板亮起 →「执行保通路径规划」→ 将禁行设施的绑定边加入 `disabledEdges` 重解 → 地图叠加第二条路线 + 对比卡（里程差/时长差/绕过的设施）。

**流程 D · 人工干预与专项**（新增，两个自定义能力）：
- **人工改判**：清单条目 →「改判」→ 选 PASS / CONDITIONAL / BLOCKED + 填原因 → 条目标"人工"徽标，规则判定被覆盖；可「恢复规则判定」。改判为 BLOCKED 时提示可加入禁行集合（不自动改路径，点保通才生效）。
- **专项评估**：清单条目 →「专项评估」→ 弹出该桥隧档案 + 当前车辆下的五维判定明细（含余量，如"设计荷载 55t − 车重 60t = **超 5t**"）。**入口不限于沿线**——11 座设施数量少而绑定稀疏，应支持从资产库直接任选一座评估，不必先有路径。

### 1.2 状态机（前端核心约束）

```
idle ──规划──▶ planned ──评估──▶ assessed ──保通──▶ rerouted
                 ▲                                  │
                 └──── 车辆方案变化 / 改判变化 ────────┘
坐标变化 → 直接回到 idle（现有 watch 已如此）
```

- 无车辆方案时规划照常，评估按钮禁用并提示；
- 车辆方案或改判变化 → 路径保留、评估结论失效（回到 planned），避免"旧结论配新参数"的错配；
- 保通后再改判 → 保通结果失效。

### 1.3 布局方案（三栏职责重排）

| 列 | 面板（自上而下） | 变化 |
|---|---|---|
| 左 | ① 路径规划（起终点/互换/规划按钮）② 车辆方案（下拉 + 摘要 + 「执行通行评估」）③ 沿线桥梁 ④ 沿线隧道 | 车辆方案从右列移到左列，与起终点构成"任务输入区"；清单条目加状态徽标 + 「专项评估」「改判」两个行内小按钮 |
| 中 | 地图（基线路径青色 + 保通路径橙色 + 四色设施标记）+ 底部页签：路径方案信息 / **评估结论** / 路网与计算状态 / 评估日志 | 底部页签从 3 → 4；评估结论页含不满足清单与绕行对比 |
| 右 | ① 通行评估结论（四色统计 + 最严结论 + 不满足清单）② 保通路径规划（禁行集合 + 触发按钮 + 对比卡）③ 重车任务配置（参数详情 + 编辑弹窗） | 现右侧"沿线桥隧判定"统计并入左列清单头部筛选条；右列让位给结论与保通两个结果面板 |

线上颜色沿用平台约定：主路径 `#45e4ff`、保通绕行 `#ff6b35`（与灾害影响环同源，语义"受阻绕行"）、设施四色红/黄/橙灰绿沿用任务结果四色。

### 1.4 接口编排（不改动 `/heavy/plan`）

```
POST /api/heavy/route-assess     ← 新增：编排 = plan + 五维判定 + 落任务
  入参: origin/destination 4 坐标, vehicle{7 参数} 或 vehicleProfileId,
        manualOverrides:[{assetId,status,reason}]
  返回: plan 全部字段 + assessments[]（每设施五维+综合+evidence）
        + conclusion（沿线最严）+ taskId
  落库: analysis_task(module_type='HEAVY_ROUTE') + ASSET 级 addResult

POST /api/heavy/route-reroute    ← 新增：保通重算
  入参: 同上 + closedAssetIds[]（评估 BLOCKED + 人工禁行的并集，前端收集）
  返回: 新路径 + 新沿线评估 + 对比（distanceDeltaKm / durationDeltaMin /
        avoidedAssets）+ unreachableReason（禁行后无解的优雅失败）
```

- 两个端点分开，保留"保通是显式决策"的产品语义；
- 新任务类型 `HEAVY_ROUTE` 与旧 `HEAVY` 隔离，首页重车汇总不被新任务污染；
- 旧 `/heavy/evaluate` 保留兼容，页面不再调用。

### 1.5 人工改判的数据形态

- **本期：任务级**。`manualOverrides` 只随请求生效，随任务存入 `input_json`，可回放；不建表，不跨任务。
- **二期：库级**。`asset_manual_status`（asset_id, effective_status, reason, operator, created_at），跨任务生效，走管理端；到期或撤销恢复规则判定。
- 语义规则：改判覆盖的是**综合结论**（source=MANUAL），原始规则判定仍计算并保留展示（"规则：BLOCKED / 人工：放行"），答辩时可解释。

## 2. 调研二：属性普查与判定方法设计

### 2.1 属性全景（数据库实际存在）

**路网边 `road_edge`（路段级判定可用）**

| 属性 | 判定用途 |
|---|---|
| `length_m` / `road_name` / `road_ref` / `road_class` | 权重 / 展示 |
| `design_speed_kmh` | 路段限速 → 速度维度 D4 |
| `lane_count` / `one_way` | 展示（one_way 当前图未生效） |
| `source_bridge_flag` / `source_tunnel_flag` | 仅候选提示，不参与判定（数据模型文档口径） |

**设施公共 `transport_asset`**

| 属性 | 判定用途 |
|---|---|
| `service_status`（IN_SERVICE / MAINTENANCE / CLOSED） | 管理维度 D1 |
| `design_speed_kmh` | 设施限速 → D4 |
| `baseline_condition_level` + `baseline_inspection_date` | 技术状况 → D4（**取值口径待普查**） |
| `construction_year` / `design_grade` / 坐标 | 档案展示 |

**桥梁 `bridge_detail`**

| 属性 | 判定用途 |
|---|---|
| `design_load_ton`（主）/ `design_load_grade`（辅证） | 承载维度 D3 |
| `vertical_clearance_m` / `horizontal_clearance_m` | 净空维度 D2（**现行 judge 对桥梁不查净空，建议启用**——跨线桥场景） |
| 桥型/跨数/墩/材料/支座/抗震挡块等 18 列 | **不进重车判定**——属方法线 A 易损性口径，避免口径混用 |

**隧道 `tunnel_detail`**

| 属性 | 判定用途 |
|---|---|
| `vertical_clearance_m` / `horizontal_clearance_m` | 净空维度 D2 |
| `lane_count` | 可选（与车宽联动意义有限） |
| 断面/埋深/衬砌/围岩等 | 不进重车判定（同上） |

**车辆（当前 localStorage 7 参数）**

| 参数 | 判定用途 |
|---|---|
| `grossWeightTon` | D3 承载 + 轴限 |
| `vehicleHeightM` / `vehicleWidthM` | D2 净空 |
| `axleCount` | D3 轴限校验（**现行 judge 未使用，建议启用**） |
| `plannedSpeedKmh` | D4 速度 |
| `vehicleLengthM` | 档案（无转弯半径数据，暂不判定） |

### 2.2 判定方法：五维规则链

现行 `judge()` 是"单刀直入"（桥梁只看荷载、隧道只看净空）。建议重构为**分维度判定、综合取最严**，每个维度独立给出 PASS / CONDITIONAL / BLOCKED / PENDING_DATA 与证据：

| 维度 | 对象 | 依据 | 规则（含现行规则，全部保留） |
|---|---|---|---|
| **D1 管理状态** | 全部设施 | `service_status` + 人工改判 | CLOSED → BLOCKED；MAINTENANCE → CONDITIONAL（现行只有 CLOSED，建议补 MAINTENANCE）；MANUAL → 按改判值 |
| **D2 净空** | 桥 + 隧 | `vertical/horizontal_clearance_m` vs 车高/车宽 | 缺 → PENDING_DATA；超 → BLOCKED；≥90% → CONDITIONAL（现行规则，**扩展到桥梁**） |
| **D3 承载** | 桥梁 | `design_load_ton` vs 总重；轴数 × 总重 | 缺 → PENDING_DATA；超 → BLOCKED；利用率 ≥85% → CONDITIONAL（现行规则）；**新增轴限校验**：按 GB1589-2016 最大允许总质量（2 轴 18t / 3 轴 25t / 4 轴 31t / 5 轴 43t / 6 轴及以上 49t）超限 → CONDITIONAL"超限运输，需办理许可"（治超口径，与桥梁技术判定并列展示，不互相覆盖） |
| **D4 速度与状况** | 全部 + 路段 | 设施/道路 `design_speed_kmh` vs 计划速度；`baseline_condition_level` | 计划速度超限速 → CONDITIONAL"需按限速通行"；技术状况三类 → CONDITIONAL、四类及以上 → BLOCKED（**取值口径与映射需普查确认**，参照 JTG 5120 桥涵养护规范方向） |
| **D5 人工改判** | 指定设施 | `manualOverrides` | 覆盖综合结论，保留规则结果并排展示 |

综合状态 = 各维度最严（PENDING_DATA 不拖累其余维度已明确的 BLOCKED）。

**输出证据结构**（每个设施）：

```json
{ "assetId": 7, "assetName": "某长江大桥", "status": "BLOCKED", "source": "RULE",
  "dimensions": [
    { "dimension": "LOAD", "status": "BLOCKED",
      "fields": { "designLoadTon": 55, "grossWeightTon": 100 },
      "margin": -45, "unit": "t", "text": "总重 100t 超过设计荷载 55t（超 45t）" },
    { "dimension": "CLEARANCE", "status": "PASS", "margin": 0.5, "unit": "m", "text": "…" }
  ] }
```

`margin`（余量：荷载差吨数 / 净空差米数）是界面上一目了然的增量，也呼应"证据链"的长期缺口。

### 2.3 数据就绪度风险（普查先行，§4）

五维规则里 4 处依赖**未知是否填值**的字段：`design_load_ton`（现行判定已用，应有值）、桥梁净空两列（现行**未用**，很可能空）、`baseline_condition_level`、`service_status` 中 MAINTENANCE 是否出现。空值多 → PENDING_DATA 占比高，界面"判不出东西"。**先跑普查再定 D2 桥梁维度与 D4 状况维度是否启用**。

### 2.4 专项评估与多方案试算

- 专项评估 = 同一套五维规则对单个设施 + 任意车辆参数，**不依赖路径**；
- 多方案试算 = 同一设施 × N 个已保存车辆方案的判定矩阵（一行一方案，红黄绿一眼扫完）；
- 两者复用同一规则组件，无新算法，纯界面与接口组织。

## 3. 风险与已知边界

## 4. 阶段 0 数据普查（只读，一次跑完）

```sql
SELECT a.id, a.asset_name, a.asset_type, a.service_status,
       a.baseline_condition_level, a.baseline_inspection_date,
       a.design_grade, a.design_speed_kmh, a.construction_year,
       b.design_load_ton, b.design_load_grade,
       b.vertical_clearance_m AS bridge_v, b.horizontal_clearance_m AS bridge_h,
       t.vertical_clearance_m AS tunnel_v, t.horizontal_clearance_m AS tunnel_h,
       t.lane_count AS tunnel_lanes
FROM transport_asset a
LEFT JOIN bridge_detail b ON b.asset_id = a.id
LEFT JOIN tunnel_detail t ON t.asset_id = a.id
ORDER BY a.asset_type, a.asset_code;
```

11 行一屏看完。需回答：① 每列空值率；② `baseline_condition_level` 取值枚举；③ 有无 MAINTENANCE/CLOSED；④ 桥梁净空是否可信。结论回填 §2.2 / §2.3。

## 5. 建议落地顺序（每步独立可验收）

1. **数据普查**（半天）→ 确定 D2 桥梁维度、D4 状况维度是否启用；
2. **规则组件抽取**：`judge()` → `FacilityRuleService`，五维化 + evidence 结构，纯后端逻辑 + 单测（不动任何接口）；
3. **编排端点** `/heavy/route-assess`：plan + 判定 + `HEAVY_ROUTE` 落库；
4. **前端**：状态机 + 清单四色 + 评估结论面板 + 底部"评估结论"页签；
5. **保通**：`/heavy/route-reroute` + 双路径显示 + 对比卡；
6. **人工改判 + 专项评估弹窗**（含多方案试算）；
7. **可选**：车辆方案入库（`vehicle_profile` 表）、`one_way` 生效、速度维度按路段展开。
